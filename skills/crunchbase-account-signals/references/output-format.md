# Account Signals output

Use `output-contract.md`. State as-of date, accepted event window and signal types, requested/confirmed book size, coverage and displayed/exported count. Preserve the helper's order and score eligibility. Unknown/partial evidence is not a low score. Show unscored evidence separately; never call an unscored row ranked.

## Weekly or requested current review

Use call_list for a concise display (up to the accepted display count), with linked company, dated sourced signal and its type. Do not fill a short signal list with momentum-only accounts. For each, separately label a seller-fit hypothesis (offering → buyer → supported product evidence), why this signal may matter, and one question to confirm. If fit is unclear, say so; do not invent a need or silently remove the account. Product-neutral mode omits seller-specific claims.

Put a clickable source reference beside each displayed event, with the event date and source clearly labeled. Prefer the returned event/article URL; when only a canonical Crunchbase record is available, link and label that record. If no source URL was returned, say so rather than inventing one. A company-profile link alone is not an event citation when a more specific returned source is available.

Optional contacts must be returned public professional names/titles, labeled as Crunchbase or CRM; no email/phone. A known CRM relationship can change the suggested approach, never the external score. Do not infer deal health from inactivity. Preserve source links and fact dates. Predictions retain provider likelihood, generation date and returned horizon; do not imply cash, available budget, completed acquisition or readiness to buy.

## Plays, feeds and alerts

Show plays only when requested: group membership/count, common dated trigger, a conditional seller-specific theme and a question. The helper's default theme is a hypothesis, never a fact about the members. A feed is within the established book; name the file and distinguish newly observed/predicted from ongoing predictions. New prediction means a supported state transition, not simply a first fetched reading.

Alerts use only the helper's returned alerts. A first persistent run is a baseline, not a batch of new alerts. An unchanged recurring run stays quiet unless status updates were requested. If incomplete, report the failed dependency and unchanged baseline; do not claim nothing changed.

Link generated files with absolute paths. Include material limitations and rejected/unresolved counts, not every empty optional field. Exported scores and ranks stay exactly as computed. End with the strongest question that could change the proposed approach. No messages are sent and no CRM updates occur.
