# Scoring and normalized artifact contract

Python 3.10+, standard library. From this skill directory run `python3 scripts/score_prospects.py score --input candidates.json --csv accounts.csv > result.json`. Add `--state previous.json` for a comparison; append `--write-state` only on the final complete pass. Relative CLI paths refer to your chosen working directory. The helper never calls a network service.

Input schema version 1; rubric version `gtm-1`. Both scoring skills bundle identical `scripts/scoring.py`; they must remain byte-identical and pass parity tests. No legacy work-directory/query-plan CLI is supported.

```json
{"schema_version":1,"run":{"today":"2026-11-05","complete":true,"scope_id":"us-fintech-accepted-v1","mode":"icp","count":50},"candidates":[{"uuid":"fixture-org-1","permalink":"lumenquill-dental","name":"Lumenquill Dental","url":"https://www.crunchbase.com/organization/lumenquill-dental","domain":"lumenquill.example","growth_score":80,"growth_tier":null,"heat_score":60,"heat_delta":0,"last_funding_at":"2026-09-01","last_funding_type":"series_b","last_funding_usd":20000000}]}
```

The example assumes the requested growth tier was unavailable (record that retrieval limitation alongside real inputs). It scores 80: growth 80 × .4 + heat 60 × .3 + funding 100 × .3. A recent completed round reaches the maximum possible funding value, so a missing prediction cannot change that maximum. A missing growth or heat factor instead yields `score:null`, `tier:null`, `status:"insufficient_evidence"`. The known components remain available in `points`; `coverage` records observed/required factor counts and missing names.

## Normalize evidence

- Each candidate requires canonical `uuid`, `permalink`, `name` and returned organization `url`. Deduplicate by UUID; reconcile conflicting duplicate evidence before invocation. An unconfirmed input does not belong in candidates; disclose it separately.
- Unwrap returned property values. Map money only from `value_usd`, keeping null and explicit zero distinct. Do not convert raw foreign-currency values into USD by assumption. Preserve precision notes in the result narrative.
- Scores are finite numeric values 0–100; `heat_delta` is -100–100. Do not pass booleans as numbers. Completed-event dates are day-precision ISO dates no later than `run.today`. Exclude and disclose imprecise or invalid dates from day-sensitive calculations; never invent day precision. The helper rejects malformed/future dates.
- `growth_tier` maps the returned growth prediction tier; `funding_tier` maps the funding prediction tier. Recognized tier values are `p100_positive_high`, `p200_positive_low`, `p300_neutral`, `p400_negative_low`, `p500_negative_high`; confirm live field contracts rather than forcing a new value into this map.
- `last_funding_at`, `last_funding_type` and `last_funding_usd` describe the latest new-money round; secondary sales, post-IPO secondary sales and non-equity assistance do not count. If the last recorded event is excluded, retrieve earlier qualifying rounds. Investor `last_fund_at`/`last_fund_usd` describe the latest completed fund close; the newer eligible date wins.
- To establish zero completed-funding evidence after a complete scoped query, provide `funding_observation:{"source":"Crunchbase","complete":true,"as_of":"2026-11-05","query_scope":"accepted full completed-funding scope","no_completed_funding":true}`. This means no returned qualifying record in that scope, not that financing never occurred.
- To establish a zero prediction component after complete retrieval, provide analogous `prediction_observation` with `no_prediction:true` and the queried scope. Do not set either observation for unavailable access, truncated results, an unqueried field or a null profile value.
- A no-record observation requires a complete relevant history/window for this rubric; a narrow date search cannot establish zero outside its window. Preserve this distinction in the scope description. Funding remains unknown when its maximum cannot be established from known recency/prediction components.
- `customer_peer` entries require canonical customer identifier, direction (`fwd`/`rev`) and nonempty `shared` micro-industry evidence. Exclude the customer's own account from the bonus. The model cannot assign a bonus merely from a description.
- `exclude` supports canonical `uuids`, `permalinks`, exact normalized `domains`. Resolve name-only exclusions before invocation. `seeds` carry canonical `uuid` and optional returned `permalink`; every `similar` row must name one of those accepted seed identifiers in `seed`, with `dir` set to `fwd`/`rev` and a nonempty `shared` list of returned micro-industries. Reject unrelated-seed evidence. `segment` preserves grouping from the accepted search.

## Heuristic and configurable tiers

Default weights: growth 40%, heat 30%, funding 30%. Growth is the average of returned tier points (100/70/40/15/0) and numeric growth score, or the one available measurement after the retrieval check in `workflow.md`. Request both supported organization growth fields before using this fallback; preserve null for a requested-but-missing measurement and record its unavailability, rather than silently omitting an unrequested field. Heat is the returned heat score plus half its returned 90-day delta, clamped to 0–100; no delta leaves the level unchanged. Funding takes the higher known completed-financing recency and prediction points. Recency is 100 through 6 full calendar months, 75 through 12, 50 through 24, 25 through 36, else 0. Predicted funding points are 75/40/0/0/0. Public companies receive the disclosed neutral funding value 50.

An optional `raise` factor (default weight zero) maps tiers to 100/75/40/15/0. Including it alongside funding double-weights prediction evidence; disclose that choice. Known customer similarity adds 10 after the weighted average, capped at 100. Default tiers: A ≥70, B ≥50, C below 50. Closed companies remain explicitly closed and untiered; never route them as ordinary Tier C opportunities.

Override through `rubric:{"weights":{"growth":50,"heat":20,"funding":30},"tiers":[75,55],"customer_bonus":0}`. Weights must be finite/nonnegative with positive total; divide by their supplied total. A positive-weight factor that is unknown makes the account unscored; never silently drop or reweight it. Zero-weight factors do not block eligibility. Fixed cutoffs stay fixed even if every account lands in one tier. These are commercial review heuristics, not empirical buying probabilities or proof of available budget.

## Outputs and handoff

JSON includes `schema_version`, `rubric_version`, `workflow`, `as_of`, `scope_id`, `complete`, `rubric`, input/exclusion/eligibility counts, `rows`, and `list_uuids`. Every row retains canonical identity, returned source values, score, tier, status, points, coverage, risk flags and rank. Only fully scored active rows receive a rank or become `list_uuids`; explicitly saving a different reviewed set requires canonical reconciliation under the saved-list contract.

CSV columns: `UUID,Permalink,Name,Domain,Tier,Score,Status,Rank,Group,Coverage,Missing factors,Crunchbase profile,CRM ID,CRM Account Name,Owner,Open deals,Deal stage,Open amount,Open amount currency,Open amount status,Next close date,Won deals,Last won date,Next step`. Unscored score/tier/rank cells remain blank. Formula-like text is prefixed with an apostrophe for spreadsheet safety; canonical identity is carried separately. Use UUID to hand the book between skills, not normalized names. Preserve the same scope and source as-of date. The JSON is the lossless handoff; CSV is a user-facing review/import artifact.

Scored accounts sort descending by score, then name and UUID, with unscored records following. Prospect count limits apply after exclusions; prioritization retains every confirmed account. The result describes the retrieved pool; do not call a bounded pool's top rows the global best prospects. Always disclose retrieved/reported counts and any unscored or unresolved accounts.

## CRM reimport identity

Attach approved CRM fields to a candidate as `crm_accounts:[{"crm_id":"source-account-id","crm_name":"original account name","owner":"rep name","open_deals":1,"deal_stage":"Qualification","open_amount":10000,"open_amount_currency":"USD","open_amount_status":"complete","next_close_date":"2026-12-01","won_deals":0,"last_won_date":null,"next_step":"Recorded next step"}]`. Use only the fields shown; no phone, email, private contact details or unrequested notes. These values are passthrough CRM records, not scoring inputs or verified Crunchbase facts. A CRM account ID must map to exactly one confirmed Crunchbase UUID in the input. Conflicting mappings fail rather than producing an import that could overwrite a different account.

For two CRM accounts confirmed as the same company, keep both entries with distinct CRM IDs on one canonical candidate. CSV emits one row per CRM account with the same Crunchbase UUID and derived score; count companies and CRM records separately. Never match reimports by name. The generated CSV remains a proposed import artifact; no CRM update has occurred. Map columns to the destination's verified custom field schema only when requested. Preserve original account IDs and owner/deal context; do not invent field API names.

### Export adapters

Optional `--format clay|crm|hubspot` preserves the same rows/IDs/values while mapping derived-field headers for the requested destination. Generic `csv` remains the lossless default. Clay uses `Crunchbase UUID`, `CB Tier`, `CB Score`, `CB Score Status`, `CB Coverage`. Salesforce-style `crm` maps CRM ID to `Id` and derived columns to `Crunchbase_UUID__c`, `CB_Tier__c`, `CB_Score__c`, `CB_Score_Status__c`, `CB_Coverage__c`, `Crunchbase_Profile__c`. HubSpot uses `Record ID` for CRM ID and the human-readable CB headers. These are proposed import-column names, not proof that custom fields exist in the destination. Verify destination fields and the user's mapping before import; do not claim an update. Owner names remain owner names, never fabricated owner IDs.

Monitoring state advances only after CSV output, when requested, and the complete JSON stdout result have been written and flushed successfully. Redirect stdout to a durable result file for recurring runs; a broken output pipe preserves the prior state. Treat a nonzero exit as failure even when an output file exists, and serialize runs sharing a state path.

Preserve the CRM parser’s `Open amount currency` and `Open amount status` as `open_amount_currency` and `open_amount_status` alongside `open_amount`. A blank amount remains null/blank, never zero; mixed/unknown currencies remain unaggregated. All export adapters retain these fields. Keep `crm-deals.json` alongside the scored artifact for original per-deal amount/currency evidence; the scoring artifact does not replace that sidecar.
